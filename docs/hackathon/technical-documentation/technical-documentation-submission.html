Summary

Stocktrails is a Chrome browser extension. It records which stocks an investor looks at on finance portals, when, for how long and on which kind of page, together with the calls they make (Positive, Neutral or Negative, with an optional target, horizon and note). Investors can import their broker's transaction export, which is read and stored only on their device.

On top of these two records sits a behavioural finance agent. It recognises the investor's own biases with statistical tests, recommends a concrete rule for each only after checking that the rule would have improved later trades it had not seen, lets the investor adopt the rule with one click, then tracks adherence and checks intended buys against adopted rules. An assistant answers questions about the investor's data by choosing read-only tools that run on the device.

The agent also measures the value it adds. Next to the investor's actual portfolio it keeps a paper portfolio that makes the same buys under the rules the investor adopted. The gap between the two, per buy and with a confidence range, is what keeping one's own rules is worth in returns. The investor sees the benefit in their own numbers, not as a promise.

Two deciders, in parallelVerdicts and the rules agent are deterministic, tested code. The AI agent is a language model, stochastic by nature, deciding on the same statistics; each decision is saved once and compared.
Trades stay localImported trades, amounts and identifiers never leave the device. Three filters guard what does.

1System architecture

The product is local-first. The client is a Chrome Manifest V3 extension: a content script on finance portals, a service worker, and a dashboard page that holds all analysis. A Supabase project in the EU provides sign-in, synchronisation of attention data between a user's browsers, anonymous community aggregates and a small set of edge functions. The heavy analysis runs in the browser.

1.3Capture and sync

Capture needs no click. The content script polls the URL every 1.5 seconds; a new ticker becomes an attention event. Each event is written twice: to the daily set, where repeat views within 60 minutes collapse into one row with a view counter, and to the intraday set, which keeps every view. All writes land locally first, so the dashboard works offline.

Synchronisation between a user's browsers uses two cursors because push and pull ask different questions. The push cursor compares local timestamps with local timestamps. The pull cursor uses the server's own receive time (synced_at), because a row captured early but uploaded late would otherwise be invisible to devices whose cursor had moved past its capture time. Pulls page by keyset in blocks of 1000 rows, since PostgREST truncates responses at that size and offset paging skipped rows that changed during a pull.

2Core algorithms

The central design decision is the division of labour. Everything that produces a number or a verdict is deterministic JavaScript, tested without a model. The model is used for four things only: choosing which read-only tools to run for a question, putting the returned results into words, proposing actions the user may approve, and, as one of two paper-trading agents, making decisions that are compared with the user's and the rules agent's.

2.3Decisions and outcomes

Fills of one instrument on one side on one day form a decision. Savings-plan executions, derivatives, bonds and crypto are set aside, as are decisions made before any research was recorded. The outcome of a buy is its excess return over the NASDAQ Composite (^IXIC) from the close of the trade day, over 21 trading days, and over 63 days for calls. Holdings that existed before the export begins are inferred from sales larger than the known position.

Context is measured from bars before the trade day, so nothing the investor could not have seen enters a feature. Volatility is the standard deviation of 20 daily returns; the buy is then placed by percentile among all trading days of the covered period, so that "you buy in turbulent markets" is judged against how often markets are turbulent. Size is judged against the investor's median buy over the previous 6 months, so a growing portfolio does not read as buying bigger.

2.4The circular shift test

Markets stay calm or turbulent for weeks, and buying comes in bursts. Neighbouring days and neighbouring buys are therefore alike, and an ordinary bootstrap gives ranges that are too narrow. Instead, the whole pattern of buys is slid along the calendar by every possible offset, wrapping around at the end, and each statistic is recomputed. The buys keep their spacing and the market keeps its stretches; only their alignment is broken. The distribution over all offsets gives the 99% range and the p-value of the observed statistic (shiftTest).

2.5Rules and walk-forward validation

Each bias maps to one or more rules, for example "wait after a run-up", "sleep on it", "avoid your worst time of day" or "cap the size in turbulent markets". A rule has a grid of settings, a flag (the rule says do not) and a gain: what not doing it would have been worth against the NASDAQ, assuming the skipped money earns the market. A cap rule scales the size instead of skipping.

fit chooses the setting that maximises

score(s) = mean_gain(s) × √ n_flagged(s) subject to n_flagged(s) ≥ 5, n_flagged(s) ≤ 0.6 × n, mean_gain(s) > 0

walkForward orders decisions in time. The first half is only ever used for training. The rest is cut into up to six blocks. For each block, the rule is fitted on decisions whose outcome was already known when the block began: a buy's outcome takes a month to arrive, so the decisions of the month before the block are embargoed. The fitted setting is then applied to the block. A fold in which no setting helped recommends nothing for that block. Only the gains on the later blocks are pooled and given a bootstrap range.

2.6Adherence and the pre-trade check

After adoption, the coach reports the share of decisions that broke the rule against the same share over an equally long stretch before adoption, with a Newcombe interval for the change, and compares the outcome of decisions that kept the rule with those that broke it, with a bootstrap range. It is reported as an association, since nobody was assigned to comply. The pre-trade check takes an intended buy (stock and amount), measures the same features as of now, and lists which adopted rules object, which cannot be checked, and any reminder the user set for that stock. Every check is saved on the device with its inputs and the rule versions in force, so checks can be evaluated later.

2.7The assistant agent loop

The assistant works in steps, at most five requests per question. Each request carries the question, with stocks replaced by aliases, and the results gathered so far. The model either names up to four more tools from a fixed read-only catalogue, or answers. The tools run in the browser, so the model can look further when a first result raises a question, for example by reading a rule's details after seeing the biases, or trying a rule with another setting. The fifth step must answer, and a tool call it already has is dropped. The browser then checks every number in the reply against the results and marks any it cannot find.

2.8Two agents with paper portfolios

To show what following the rules would have meant in money terms, two agents trade paper portfolios on the investor's own buys and on the stocks they looked at. The rules agent (src/shadow.js, no model) keeps, each month, only the rules that had held up out of sample on outcomes known by then, plus any rules the investor adopted. For each candidate it buys at once, waits until no active rule objects (re-checking 1 to 10 trading days later), or passes. The AI agent receives each candidate as of that day (alias, "day N", ratios, the rules agent's view) in requests of 15, and is asked only about moments at most two days old. Every decision is saved once with its time; there is no backfill, so the model cannot know what happened next.

2.9Measured value added

Adherence tracking answers the question an investor cares about: do my own rules make me money? From the first imported buy, the app keeps three portfolios side by side on the same money, valued daily in the investor's currency:

  • the investor's actual portfolio;
  • the same buys made under the investor's adopted rules: the rules agent with every adopted rule applied, so it waits or passes where a rule objects and cuts the size where a cap applies;
  • the NASDAQ as a benchmark.

The gap between the first two is the value of keeping one's own rules. It is reported per buy at 21, 63 and 126 trading days, with a 99% bootstrap range, and separately for the period before and after the investor started using the app. The adherence view adds the direct comparison: decisions that kept an adopted rule against those that broke it. The investor therefore sees the benefit of the agent in their own returns, as a measured difference rather than a forecast.

3Security design

The security design follows from one principle: the most sensitive data, an investor's trades, should not exist anywhere it does not need to. Raw trades are parsed in the browser and kept in IndexedDB on the device. The cloud receives attention events for the user's own account under row-level security, and the model receives only de-identified results that pass three filters. The agent has no path to an order.

Trust boundaries, in order of exposure: (1) finance portal pages, which are untrusted and may read the DOM around the capture card; (2) the device, which holds everything; (3) the Supabase project, which holds synced attention and counters; (4) model and data providers, which see only what the edge functions send.

3.2Permission tiers

The agent's authority is fixed in code. The server validates every tool call and proposed action, and the browser executes only what the user confirms.

3.3Cloud authorisation

Row-level security is enabled on every table. Owner policies use user_id = auth.uid() for reading and writing. Admin reads go through is_admin(), which a user cannot set because profiles has a column-level UPDATE grant. Service-only tables (ai_usage, crowd_notified) have no policies, and their functions are revoked from anon and authenticated. Security-definer functions pin search_path. Community views return a cell only when enough distinct users stand behind it.

3.5Security review and known risks

A read-only code review on 17 October 2026 covered database authorisation, edge functions, the extension, and build and hosting. Each reported issue was re-checked against the code by a second, independent reviewer. It confirmed three high-severity findings and a set of medium and low ones. 3.6Regulatory compliance: EU, China, United States

Three design choices carry most of the compliance load in every jurisdiction: trades and account data never leave the browser, the product describes the investor's own behaviour instead of recommending securities, and the model is a replaceable explainer behind a deny-by-default gate. The tables show how each rule is met today and what a launch in that market would add. The one feature that needs a market-by-market decision is the AI agent's stock-level paper verdict, which is the closest the product comes to investment advice.
